## v1.40.0

**Release Date:** October 17, 2026

**Release Type:** Minor Release

**OpenAPI Spec:** [Download v1.40.0 spec](/api-reference/v01.40.00/openapi-v01.40.00.json)

### Signing page buttons

Two new settings control the buttons that signers and approvers see on the signing page, hosted or embedded:

- `allow_decline` shows the **Decline to Sign** button. When it is `false`, the button is hidden for every signer and approver, and Firma.dev also refuses a decline. No one can decline the signing request in Firma.dev, so it can only be stopped by cancelling it.
- `show_save_for_later` shows the **Save & Finish Later** button. When it is `false`, only the button is hidden.

Firma.dev uses the signing request's value. When it is `null`, the workspace's value applies, and when that is `null` too, the company's. The company default is `true`, so signing pages are unchanged until you set a value.

| Level | Set with | Values |
|---|---|---|
| Company | `PUT /company/settings` | `true` or `false`. Default `true` |
| Workspace | `PUT /workspace/{workspace_id}/settings` | `true`, `false`, or `null` to use the company value |
| Template | `settings` on `POST /templates` and `PATCH /templates/{id}`; `template_properties.settings` on `PUT /templates/{id}` | `true`, `false`, or `null` |
| Signing request | `settings` on `POST /signing-requests`, `POST /signing-requests/create-and-send`, and `PATCH /signing-requests/{id}`; `signing_request_properties.settings` on `PUT /signing-requests/{id}` | `true`, `false`, or `null` to use the workspace value |

- A signing request created from a template (`template_id` on `POST /signing-requests` and `POST /signing-requests/create-and-send`, or `POST /templates/{id}/duplicate`) copies the template's values when it is created. On the two create routes, a value in the request's `settings` replaces the template's; `null` there means the workspace value. `POST /templates/{id}/duplicate` always copies the template's values. Changing the template later does not change signing requests already created from it.
- `POST /templates/{id}/copy` copies both values to the new template.
- A change to the workspace or company value applies to every signing request whose own value is `null`, including requests already sent and requests created before this release.
- Responses return the values as `true`, `false`, or `null`: in `settings` on templates (`GET /templates`, `GET /templates/{id}`, `POST /templates`, `PUT /templates/{id}`) and signing requests (`GET /signing-requests`, `GET /signing-requests/{id}`, and the create responses), and at the top level of `GET /company/settings` and `GET /workspace/{workspace_id}/settings`. The company values are always `true` or `false`.
- Any other value, such as a string or a number, returns `400 VALIDATION_ERROR` naming the key (for example `settings.allow_decline must be a boolean or null`) and writes nothing. `PUT /company/settings` also refuses `null`.

### Request size limit

Since October 13, 2026, a request body larger than 6,291,456 bytes (6 MiB) returns `413 REQUEST_TOO_LARGE` with the standard `error` and `code` body. Before, the gateway answered `502`. The API reference documents it on `POST /templates`, `POST /signing-requests`, `POST /signing-requests/create-and-send`, and `POST /documents`.

To send a larger document, request an upload URL with `POST /documents`, upload the file to it, and pass `document_id` or `document_ids` instead of inline base64.

### Migration notes

- The change is additive. Requests that never send `allow_decline` or `show_save_for_later` behave as before, and both buttons stay visible until a value is set.
- If you parse responses strictly, accept the two new keys in template, signing request, workspace settings, and company settings responses.
- If you send large inline base64 documents, handle `413 REQUEST_TOO_LARGE`, or upload through `POST /documents`.

## v1.39.1

**Release Date:** October 12, 2026

**Release Type:** Patch Release

**OpenAPI Spec:** [Download v1.39.1 spec](/api-reference/v01.39.01/openapi-v01.39.01.json)

### Update, October 13, 2026

- On `POST /signing-requests` and `POST /signing-requests/create-and-send` with `template_id`, when the template has no recipients of its own and `seal_participants` is absent or `null`, inherited seals now keep their template order first (`1..k`), followed by the request's recipients (`k+1..`). Explicit replacement arrays, templates with recipients, and requests without seals retain their existing order behavior.
- Replacements through `PATCH /seals/{id}` now require `statement` with `accepted: true`, `version: 1`, `language`, `text` exactly equal to the stored `statement_text` from `GET /seals/{id}`, and `signatory_name` (`signatory_title` optional). This applies to changes in `image`, `typed`, `display_name`, `signatory_title`, or `statement`. Without `statement`, the request returns `400 SEAL_STATEMENT_REQUIRED` and writes nothing. `POST /seals` creation behavior is unchanged.
- Each replacement records its own attestation time, caller, and supplied signatory. Statement text, hash, language, statement version, and `authority_name` remain those of seal version 1. Requests already sent keep their pinned version; requests sent after replacement use the new version, whose signatory and attestation date appear on their certificates.
- Seal objects in `POST /seals`, `GET /seals`, `GET /seals/{id}`, `PATCH /seals/{id}`, and the `organization_seal.created`, `organization_seal.updated`, and `organization_seal.deleted` webhooks now include `statement_text` and `statement_hash`. Attester user and API key IDs, IP address, and user agent are excluded from these seal objects.

### Organization seals from templates

`POST /signing-requests` and `POST /signing-requests/create-and-send` with a `template_id` now copy the template's seal participants and their seal fields. The `seal_participants` key decides what happens:

- Absent or `null`: the request inherits the template's seals.
- An array: the array replaces the template's seals. The template's seal fields are not copied.
- `[]`: the request is created without seals.
- Any other type returns `400 VALIDATION_ERROR`. This is checked on every create route, with or without `template_id`.

Body fields only override template fields, so on a template that has fields a replacement array's seals cannot get a stamp field in that call, and sending returns `400 SEAL_NO_IMAGE_FIELD`. To use your own seals with their fields, create from a document, or, on `POST /signing-requests` only, use a template without fields and assign body fields with `seal_participant_temp_id`. Otherwise inherit the template's seals.

An inherited seal uses the current version of its seal. If the seal has no current version, or that version is revoked or deleted, the create returns `409 SEAL_UNAVAILABLE` and nothing is written. If at least one inherited seal is kept and organization seals are not enabled, the create returns `503 SEALS_DISABLED`.

An inherited seal that is limited to another workspace than the request's, or that the API key's company cannot see, is left out, along with its fields. It is listed in the response with `dropped: true`, after the other entries. Every other entry carries `dropped: false`.

```json
{
  "id": null,
  "order": null,
  "seal": { "id": "<seal-uuid>", "lineage_id": "<lineage-uuid>", "name": "Acme Corp", "version": 2, "display_name": "Acme Corp" },
  "seal_out_of_scope": true,
  "dropped": true
}
```

`seal` is `null` when the API key's company cannot see the seal. A company-wide seal is never left out.

#### Order with a template

When a create with `template_id` resolves at least one seal, recipients and seals are renumbered `1..n`. Inherited seals keep their positions relative to the template's recipients. Seals in a replacement array are placed by their `order`. A seal comes first when it ties with a recipient. Such a create returns `201` where it used to return `400 INVALID_SIGNING_ORDER` or `400 SEAL_ORDER_COLLISION`. The response reports the renumbered orders.

- Since October 13, 2026, if the template has no recipients and `seal_participants` is absent or `null`, inherited seals keep their template order first (`1..k`); the request's recipients follow (`k+1..`).
- On `POST /signing-requests`, a numeric `recipient_id` on a field keeps counting recipients as they would be numbered without the seal.
- Document-based creates (`document`, `document_id`, `document_ids`) with explicit seal participants are unchanged: the raw order checks apply.

#### Seal fields and sending

A seal needs at least one stamp field. Create does not check this, but sending a signing request whose seal has no stamp field returns `400 SEAL_NO_IMAGE_FIELD`. Give every seal at least one stamp field.

### Duplicating a template

Except for companies enabled for multi-document features, `POST /templates/{id}/duplicate` copies the template's seal participants and their fields into the new signing request, and returns them in `seal_participants` (`[]` when there are none). Each kept seal uses the current version of its seal. If the seal has no current version, or that version is revoked or deleted, the route returns `409 SEAL_UNAVAILABLE`. A seal limited to another workspace than the target workspace, or that the API key's company cannot see, is left out and listed with `dropped: true`. If at least one seal is kept and organization seals are not enabled, the route returns `503 SEALS_DISABLED`. Both errors are returned before anything is written.

For companies enabled for multi-document features, this route attaches the template's stored seal version as is. A seal that was replaced, revoked, or deleted since then fails when you send. The response has no `seal_participants` key.

### seal_attribute

A seal-owned text field takes `seal_attribute`: `display_name` or `signatory_title`. It sets which seal property the field prints. `POST /signing-requests` and `POST /signing-requests/create-and-send` accept it, from a document or a template. Any other value returns `400 VALIDATION_ERROR`; `null` is accepted.

- `POST /signing-requests/create-and-send` from a document now keeps `seal_attribute`. Before, it was dropped.
- A seal field copied from a template keeps the template field's formatting. `seal_attribute` on the request replaces only which property it prints.

### Templates

- `GET /templates/{id}` and `PUT /templates/{id}` return `seal_participants`, ordered by `order`, `[]` when the template has none. Each entry has the shape of seal participants elsewhere.
- `POST /templates` does not accept `seal_participants`, `recipients`, or `fields`. It ignores them and returns a `warnings` array with one string per key present, for example `seal_participants is not accepted on POST /templates and was ignored; add it with PATCH or PUT /templates/{id}`. Without those keys the response is unchanged.

### Other changes

- Fixed: `seal_participants` on `GET /signing-requests/{id}`, `GET /signing-requests`, `POST /signing-requests`, and `POST /signing-requests/create-and-send` now returns each organization seal participant with its seal (id, lineage, version, name and display name) for every company. Previously this list was empty, even though the seal itself was saved and applied correctly on the document. This fix changes only what the API returns; stored documents, signatures, and webhooks are not changed by it.
- Completion certificates now draw the applied seal's stamp, date, and text fields, and list each seal participant in the signers table, in signing order. The certificate is not generated while a seal is still outstanding (not applied, or paused). A seal applied automatically at completion, without a triggering recipient, no longer blocks the certificate; its audit line reads "after all preceding participants completed" (in the certificate's language).

### Documentation and API reference

The API reference for this version documents the following. They describe answers the API already gave.

- Each entry of `seal_participants` on `POST /signing-requests` and `POST /signing-requests/create-and-send` requires `temp_id` and `order`. `seal_id` is optional: without it the workspace's default seal is used or, when the workspace has none, the company's default seal, and the call returns `400 SEAL_UNAVAILABLE` when neither exists. The reference had `seal_id` as required and `temp_id` as optional.
- The `seal_participant` body of `PATCH /signing-requests/{id}` and `PATCH /templates/{id}` is documented as the API reads it: `id`, `seal_id`, `order`, and on signing requests `swap_to_seal_id`. The key `participant_id` that earlier references showed was never read; use `id`. Adding a seal participant answers `201` and updating or swapping one answers `200`, both with `{ "seal_participant": ... }`. These routes return `503 SEALS_DISABLED` when organization seals are not enabled and a seal participant is added or its seal is changed. On `PATCH /signing-requests/{id}`, a field that belongs to a seal participant accepts only position and page changes; other keys, `recipient_id` included, are ignored.
- A seal swap on `PATCH /signing-requests/{id}` documents its answers: `403 PROTECTED_KEY_REQUIRED` when the API key is not of the protected workspace; `404 NOT_FOUND` when the new seal does not exist, belongs to another company, or is limited to another workspace; `409 SEAL_UNAVAILABLE` when the new seal is revoked, deleted, or not the current version; `409 SEAL_MUTATION_NOT_ALLOWED` when the request was not sent or the participant is not paused; `400 SEAL_FIELD_REQUIRED` when the participant has no stamp field.
- The `200` body of `DELETE /signing-requests/{id}/seal-participants/{participant_id}` is `{ "deleted": true }`.
- The `fields` array of the `POST /signing-requests/create-and-send` response lists all active fields, including the fields owned by seal participants. Each item is the stored field record, not the `Field` shape used in requests (for example the type is in `field_type`).
- `POST /templates/{id}/copy` documents its `seal_participants` (unchanged behaviour).
- `PUT /templates/{id}` documents its `seal_participants` request array (`TemplateSealParticipantInput`), which replaces the template's seal set.
- The `400` of `POST /signing-requests/create-and-send` lists `SEAL_NO_IMAGE_FIELD` (a seal without a stamp field refused when sending).
- Settings whose `null` has a meaning (`require_otp_verification`, `require_terms_acceptance`, `allow_presigning_download`, `terms_url`, a field's `recipient_id` or `assigned_to_user_id`, `identity_editable_fields`, and the workspace settings `show_signature_frame` and `show_partial_watermark`) now state what `null` does.

### Migration notes

- For seal replacements from October 13, 2026 onward, read `GET /seals/{id}` and send `statement` on `PATCH /seals/{id}`: `accepted: true`, `version: 1`, `language`, the exact stored `statement_text` as `text`, and `signatory_name` (`signatory_title` optional). Handle `400 SEAL_STATEMENT_REQUIRED` and accept `statement_text` and `statement_hash` in seal objects.
- A `POST /signing-requests` or `POST /signing-requests/create-and-send` with `template_id` and no `seal_participants` key now inherits the template's seals. Send `"seal_participants": []` to create without them. `null` inherits too (including a client that sends `null` for an unset field).
- A `seal_participants` value that is not an array or `null` now returns `400 VALIDATION_ERROR` on `POST /signing-requests` and `POST /signing-requests/create-and-send`; before, it was ignored.
- If you parse responses strictly, accept the new keys: `dropped` on create responses, `warnings` on `POST /templates`, and `seal_participants` on `GET /templates/{id}`, `PUT /templates/{id}`, and `POST /templates/{id}/duplicate`.

## v1.39.0

<Note>
**Update, October 13, 2026:** Multi-document features are available to every company. No enablement is needed. The enablement restrictions in the original release notes below describe the initial rollout.
</Note>

**Release Date:** October 12, 2026

**Release Type:** Minor Release

**OpenAPI Spec:** [Download v1.39.0 spec](/api-reference/v01.39.00/openapi-v01.39.00.json)

### Multiple documents per template and signing request

A template or signing request can now hold up to 20 documents, with a limit of 100 MB per document set. You can create one from several uploads, then add, replace, rename, reorder, remove, and download its documents one at a time.

<Note>
Multi-document features require enablement for your workspace's company. This covers the `/documents` routes, `document_ids` with more than one id, per-document anchor tags (`anchor_tags[].document_index`), and the `documents`, `documents_version`, and `documents_layout_version` response keys. If your company is not enabled:

- The `/documents` routes return `404 NOT_FOUND`, exactly like an unknown endpoint.
- The three response keys are absent.
- `document_index` on an anchor tag is not applied: a single-document create accepts it with an unknown-property warning and uses the only document.
- `POST /templates`, `POST /signing-requests`, and `POST /signing-requests/create-and-send` with more than one entry in `document_ids` (repeated ids count) return `409 MULTI_DOCUMENT_READ_ONLY` before anything is created.
</Note>

While multi-document editing is suspended, writes to a multi-document template or signing request return `409 MULTI_DOCUMENT_READ_ONLY`. Reads keep working.

#### Creating with several documents

`POST /templates`, `POST /signing-requests`, and `POST /signing-requests/create-and-send` accept `document_ids`. Pass 1 to 20 temporary upload ids from `POST /documents`, in document order.

- Send exactly one document source: `document`, `document_id`, or `document_ids` (or `template_id` on the signing-request routes). Sending more than one returns `400 CONFLICTING_DOCUMENT_SOURCE`.
- A repeated id returns `400 DUPLICATE_DOCUMENT_ID`. More than 20 ids return `400 MAX_DOCUMENTS_EXCEEDED`. An unknown or expired upload returns `400 DOCUMENT_UPLOAD_NOT_FOUND`. A set above 100 MB returns `413 DOCUMENT_SET_TOO_LARGE`.
- `document` is no longer marked as required on `POST /templates`, because `document_id` or `document_ids` can take its place.

#### Per-document anchor tags

For enabled companies, anchor tags take a new `document_index`: the 1-based position in `document_ids` of the document to search. It is only meaningful for multi-document requests.

- With one document, `document_index` is optional and defaults to `1`.
- With more than one document, it is required. A missing value returns `400 ANCHOR_DOCUMENT_REQUIRED`; a value out of range returns `400 VALIDATION_ERROR`.

#### New endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/templates/{id}/documents` | Add a document (a temporary upload from `POST /documents`) at `position`, or last |
| `PATCH` | `/templates/{id}/documents/{document_id}` | Replace the document with a new upload (`document_id`) or rename it (`label`); send exactly one |
| `PUT` | `/templates/{id}/documents/order` | Reorder: `document_ids` must list every document of the template exactly once |
| `DELETE` | `/templates/{id}/documents/{document_id}` | Remove a document; the last remaining document cannot be removed |
| `POST` | `/signing-requests/{id}/documents` | Add a document at `position`, or last |
| `PATCH` | `/signing-requests/{id}/documents/{document_id}` | Replace or rename a document |
| `PUT` | `/signing-requests/{id}/documents/order` | Reorder the signing request's documents |
| `DELETE` | `/signing-requests/{id}/documents/{document_id}` | Remove a document |
| `GET` | `/signing-requests/{id}/documents/{document_id}/download` | Signed URL (valid for 1 hour) to one document: `type=original` (default) for the document as uploaded, `type=document` for the individually sealed document once the certificate is bound |

Every add, replace, rename, reorder, and remove returns the full document set after the change, with `documents`, `documents_version`, and `documents_layout_version`.

- A replacement must have the same number of pages, and every page must be the same size within 1 pt. Otherwise it returns `400 PAGE_COUNT_MISMATCH` or `400 DIMENSION_MISMATCH`. On a signing request, a document placed with anchor tags is replaced only when the replacement's anchors resolve exactly as stored. Otherwise it returns `400 ANCHOR_MISMATCH`.
- A sent, finished, cancelled, or declined signing request returns `409 DOCUMENT_SET_LOCKED` on every document write.
- A document id that is not part of the template or signing request returns `404 DOCUMENT_NOT_FOUND`. A missing or repeated id in a reorder returns `400 INVALID_DOCUMENT_ORDER`. Removing the last document returns `400 MIN_DOCUMENTS_REQUIRED`.
- The download returns `404 DOCUMENT_ORIGINAL_NOT_AVAILABLE` when the uploaded file is no longer stored, and `404 DOCUMENT_SIGNED_NOT_AVAILABLE` before the certificate is bound.

#### Documents in responses

For enabled companies, these responses carry `documents`, `documents_version`, and `documents_layout_version`: `GET /templates`, `GET /templates/{id}`, `POST /templates`, `PUT /templates/{id}`, `GET /signing-requests`, and `GET /signing-requests/{id}`.

- Each entry of `documents` has `document_id`, `position`, `label`, `original_filename`, `page_count`, and `document_url_kind`. Outside list responses, each entry also includes a signed `document_url`, valid for 1 hour. Signing requests also include `document_only_hash`, the SHA-256 of the individually sealed document once the certificate is bound.
- A template or signing request whose document set has never been changed returns its one document with `document_id: null`. In list responses, it shows `documents: []`.
- `documents_version` increases with every document change. `documents_layout_version` increases when documents are added, removed, or reordered.

#### Field writes on multi-document templates and signing requests

`PUT` and `PATCH` on `/templates/{id}` and `/signing-requests/{id}` accept `documents_layout_version` alongside field writes. Send the value from your last read.

- It is required for a field write when there is more than one document or the layout version is above 1. A missing value returns `409 DOCUMENTS_LAYOUT_VERSION_REQUIRED`.
- A stale value returns `409 DOCUMENT_SET_VERSION_CONFLICT`. Reload and retry.
- A value that is not a non-negative integer returns `400 VALIDATION_ERROR` with the key `documents_layout_version`. A field placed on a page beyond its document's page count returns `400 VALIDATION_ERROR` with the key `page`.
- An inline `document` on `PATCH /signing-requests/{id}` for a request with more than one document returns `409 MULTI_DOCUMENT_REPLACE_UNSUPPORTED`. Use the `/documents` routes instead.

#### Templates with several documents

- `POST /templates/{id}/copy` copies a template with more than one document as a template with one merged document. The content and the absolute page numbers of its fields are kept. The per-document labels and positions are not carried over.

#### Create and send conflicts

`POST /signing-requests/create-and-send` can return `409` with `MULTI_DOCUMENT_READ_ONLY`, `SEND_IN_PROGRESS`, `SEND_EFFECTS_EXIST`, `ALREADY_SENT`, `DOCUMENT_SET_BUSY`, `DOCUMENT_SET_INCONSISTENT`, `DOCUMENT_SET_VERSION_CONFLICT`, or `DOCUMENT_SET_DISPATCH_STALE`.

`SEND_EFFECTS_EXIST` and `ALREADY_SENT` can also carry `signing_request_id`. It is present when the signing request this call created was kept. Recover that request instead of retrying, because a retry creates a second request. Without `signing_request_id`, no request was kept.

### Participant order

Signers, approvers, and organization seal participants share one order space. CC recipients are stored separately and never take a position in it.

- `PATCH /templates/{id}` and `PATCH /signing-requests/{id}` move a recipient or seal participant by shift-insert: every participant between the old and new positions is renumbered. A target position above `n` returns `400 INVALID_SIGNING_ORDER`. An `order` below 1 returns `400 INVALID_SIGNING_ORDER` for a recipient and `400 VALIDATION_ERROR` for a seal participant.
- A new Signer or Approver on those routes is inserted at `order` within `[1..n+1]`, or appended when `order` is omitted. `order: 0` or a position outside that range returns `400 INVALID_SIGNING_ORDER`.
- A new seal participant requires `order` as a positive integer. A missing or zero `order` returns `400 VALIDATION_ERROR`; a position outside `[1..n+1]` returns `400 INVALID_SIGNING_ORDER`.
- On `PATCH /templates/{id}` and `PATCH /signing-requests/{id}`, the seal must belong to your company: another company's seal returns `404 NOT_FOUND`. A revoked, deleted, or superseded seal returns `400 SEAL_UNAVAILABLE`. A seal scoped to another workspace returns `400 SEAL_UNAVAILABLE` on `PATCH /signing-requests/{id}`. On `PATCH /templates/{id}` it returns `404 NOT_FOUND` when you add a seal participant or move one (`order` set); changing only the seal of an existing participant (`id` and `seal_id`, no `order`) does not check the seal's workspace.
- On a sent signing request, `PATCH /signing-requests/{id}` returns `409 ALREADY_SENT`, except a protected caller's swap of a paused seal participant. Removing a seal participant with `DELETE /signing-requests/{id}/seal-participants/{participant_id}` returns `409 SEAL_MUTATION_NOT_ALLOWED`.
- An order change that conflicts with a seal participant that has already been applied returns `409 SIGNING_ORDER_LOCKED_APPLIED`.
- `POST /signing-requests` and `POST /signing-requests/create-and-send` without seals number recipients in array order when `use_signing_order` is false or any recipient omits `order`. With seals, every recipient needs an `order`, and recipients and seals together must form `1..n`: a missing order or a gap returns `400 INVALID_SIGNING_ORDER`, and two participants (recipients or seals) on the same order return `400 SEAL_ORDER_COLLISION`.
- `PUT /templates/{id}` applies each entry of `users` and `deleted_users` as its own participant write. If one entry fails, the entries applied before it are kept.
- `POST /templates/{id}/copy` keeps the source template's order, drops seal participants whose seal is not in scope for the target workspace (along with their fields), and compacts the remaining participants to `[1..n]`.

### Organization seal authority name

Seals returned by `POST /seals`, `GET /seals`, `GET /seals/{id}`, and `PATCH /seals/{id}` include `authority_name`, the name the seal was attested for: the company for company scope or the protected workspace, otherwise the workspace. It is `null` for seals whose lineage was created before the name was pinned; those seals certify in the company's current name.

### Other changes

- `POST /signing-requests/{id}/resend` returns `409 SEND_IN_PROGRESS` while a send of that signing request is in progress.
- Fixed: for companies enabled for multi-document signing, creating a signing request (`POST /signing-requests`) and creating and sending one (`POST /signing-requests/create-and-send`) now return each organization seal participant with its seal (id, lineage, version, name and display name) in `seal_participants`. Previously this list was empty, even though the seal itself was saved and applied correctly on the document. Signed documents, certificates and webhooks are not affected.
- Documentation only: the `POST /signing-requests/create-and-send` response now documents `seal_participants`, which it already returned. The resend response now documents `recipients_suppressed`, the number of recipients not reminded because their address is suppressed.

### Unchanged

- `PUT /signing-requests/{id}` with a field id that does not belong to the signing request still returns `400`, on multi-document requests too.
- `reminders` on `POST /signing-requests/create-and-send` work as before, including on requests created with `document_ids`.

### Migration notes

- The change is additive. Requests that never use `document_ids`, `document_index`, or the `/documents` routes behave as before, and companies that are not enabled see no new response keys.
- If you generate a client from the OpenAPI spec: `document` is optional on `POST /templates`, and the seal participant schema in signing-request responses is now named `SealParticipantApi` (previously `SealParticipant`).
- If you parse error codes strictly, accept the new codes above.
- On an enabled company, send `documents_layout_version` with field writes on templates and signing requests that have more than one document.

### CC recipients

The update endpoints now store recipients with `"designation": "CC"`, and the read endpoints now return them. Before this release they did neither.

#### Adding and updating CC recipients

- `PUT /templates/{id}` (`users[]`) and `PATCH /templates/{id}` (`user`) store CC recipients. Previously these returned `400` and `500`.
- `PUT /signing-requests/{id}` (`recipients[]`) and `PATCH /signing-requests/{id}` (`recipient`) store CC recipients. Previously `PUT` returned `200` and counted the CC in `summary.recipients_created` without storing it, and `PATCH` returned `500`.
- On `PUT /signing-requests/{id}`, a recipient that fails to save is now listed in `details.recipients` of the `400` response instead of being counted in `summary.recipients_created`.
- Existing CC recipients can be updated by `id` and removed through `deleted_users` / `deleted_recipients`, the same way as signers and approvers.
- `first_name` and `email` are required for a new CC recipient.
- `designation` is matched case-insensitively (`"CC"`, `"cc"`).

#### CC recipients in responses

CC recipients are returned with `"designation": "CC"`, after signers and approvers, by:

- `GET /signing-requests/{id}/users`
- `GET /templates/{id}/users`
- `GET /templates/{id}` and `GET /templates` (`recipients`)
- the `recipients` array of the `POST /signing-requests`, `POST /signing-requests/create-and-send`, and `PUT /signing-requests/{id}` responses

CC entries carry the same keys as the other entries on that endpoint. They never get a signing link, and keys that only apply to signing hold neutral values (for example `required_fields: []` and `ready_to_send: true`).

#### Template-based creation

- `POST /signing-requests` and `POST /signing-requests/create-and-send` with `template_id` now copy the template's CC recipients to the new signing request. A template CC is skipped when a CC with the same email (case-insensitive) is already on the request.
- A request-body recipient with `"designation": "CC"` is always added as a CC recipient. It is never matched to a template user by `template_user_id` or `order`.

#### Validation

- Changing an existing recipient between CC and Signer or Approver returns `400`. `PATCH /templates/{id}` and `PATCH /signing-requests/{id}` return the message `Cannot change designation between CC and Signer/Approver; delete the recipient and create it again`, `PUT /signing-requests/{id}` lists it in `details.recipients`, and `PUT /templates/{id}` returns the generic `Validation errors occurred`. Delete the recipient and create it again with the new designation.
- A field cannot be assigned to a CC recipient. On `PUT /signing-requests/{id}`, including for a CC created in the same request through `_temp_id`, the field error reads `Cannot assign fields to CC recipient.`; other field paths reject a CC id as an invalid recipient.
- Updating or deleting a recipient by `id` now only matches recipients that have not been deleted. An already-deleted recipient is treated as not found instead of being written to.

#### Migration notes

- No new endpoints, fields, or enum values, so the v1.37.0 spec still applies.
- Recipient lists can now include CC entries. If your code treats every entry as a signer, check `designation`.
- Signing requests created from a template that has CC recipients now include those CC recipients, and they receive the completed document. Remove the CC recipients from the template if you do not want this.
- If you relied on `PUT /signing-requests/{id}` returning `200` when a recipient failed to save, handle the `400` response.

**Release type:** Patch Release

**Released:** 2026-06-14

[Download OpenAPI Spec](/api-reference/v01.25.01/openapi-v01.25.01.json)

### Accurate error responses for create-and-send

`POST /signing-requests/create-and-send` previously returned a generic **500** whenever the send step rejected a request, hiding the real reason. It now returns the **client-actionable status** (`400`, `402`, or `422`) with a machine-readable `code` and the relevant detail:

- **`400` `VALIDATION_ERROR`** — request or send validation failed (e.g. a signer missing required information); the response includes `validation_errors`, `field_errors`, or `details` identifying what to fix.
- **`402` `INSUFFICIENT_CREDITS`** — not enough credits to send; `current_credits` reports the balance.
- **`422` `RECIPIENT_EMAIL_SUPPRESSED`** *(new)* — a recipient's email address is suppressed (previously bounced or marked as spam) and cannot be sent to.

Genuine server-side failures still return `500`. When the send step fails, the partially-created signing request is rolled back, so no orphaned draft is left behind.

**Migration guide:** No action required for clients that already treat any non-2xx response as a failure. If you previously special-cased the opaque `500` from this endpoint, switch to branching on the HTTP status / `code`: `400` and `422` mean "fix the request, then retry," `402` means "add credits."

### New Features

#### Identity Editable Fields

Signing requests now support per-field, per-signer identity editing. When configured, signers see a confirmation dialog before signing where they can review and edit specified identity fields (name, company, title, phone, address).

New settings property:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `identity_editable_fields` | `string[]` or `null` | `null` | Array of identity field keys signers can edit. `null` = disabled. |
| `notify_identity_change_email` | `boolean` | `false` | Send an email when a signer changes their identity |

- `null` - use request default
- `[]` - disabled for this signer
- `["name", "company"]` - custom fields for this signer

Example:

```json
{
  "settings": {
    "identity_editable_fields": ["name", "company"]
  },
  "recipients": [
    {
      "name": "John Doe",
      "email": "john@example.com",
      "designation": "signer",
      "order": 1,
      "identity_editable_fields": null
    },
    {
      "name": "Jane Smith",
      "email": "jane@example.com",
      "designation": "signer",
      "order": 2,
      "identity_editable_fields": []
    }
  ]
}
```

In this example, John inherits the request default (name + company editable), while Jane has identity editing explicitly disabled.

|----------|------|---------|-------------|
| `prefilled_editable` | `boolean` | `false` | When true, signers can edit prefilled values |

Available on:
- Template fields (`PATCH /templates/{id}`, `PUT /templates/{id}`)
- Signing request fields (`POST /signing-requests`, `POST /signing-requests/create-and-send`)
- Field response objects (`GET /signing-requests/{id}`)

Example - create a signing request with an editable prefilled field:

```json
{
  "fields": [
    {
      "type": "text",
      "recipient_id": "temp_1",
      "page_number": 1,
      "x": 10,
      "y": 20,
      "width": 30,
      "height": 5,
      "format_rules": {
        "prefilledData": "full_name",
        "prefilledEditable": true
      }
    }
  ]
}
```

#### Field Value Source Validation

The API now validates that fields use only one value source at a time. Requests that combine `read_only_value`, `prefilled_data`, and explicit `value` on the same field will return a `400 VALIDATION_ERROR`. This enforcement applies to:

- `POST /signing-requests`
- `POST /signing-requests/create-and-send`
- `PATCH /templates/{id}` (field creation and update)
- `PUT /templates/{id}` (field upsert)

#### Value Precedence

When `prefilled_editable` is `true` and both an explicit `value` and `prefilled_data` are set on a field, the explicit value takes precedence over the auto-populated recipient data.

### Migration Guide

No breaking changes. New features are opt-in:
- Identity editing is disabled by default (`identity_editable_fields: null`). Set it to an array of field keys to enable.
- Existing prefilled data fields remain locked (read-only) by default. Set `prefilled_editable: true` in `format_rules` to make them editable.

#### Download Signing Request Document

A new endpoint retrieves a download URL for a signing request's document. For completed signing requests, the URL points to the final signed PDF. For in-progress, cancelled, declined, or expired requests, the URL points to a partial snapshot PDF capturing the document state at the time of the last signer action.

**Endpoint:** `GET /signing-requests/{id}/download`

**Response fields:**

| Field | Type | Description |
|-------|------|-------------|
| `status` | `string` | Signing request status: `finished`, `in_progress`, `cancelled`, `declined`, or `expired` |
| `is_partial` | `boolean` | `true` when the document is a partial snapshot (not all signers completed) |
| `download_url` | `string` | Pre-signed URL to the PDF document |

| `expires_at` | `date-time` | When the `download_url` expires |

| Signing Request State | Response |
|-----------------------|----------|
| Not yet sent | `409 Conflict` — download unavailable |
| Sent, generation in progress | `503 Service Unavailable` with `Retry-After` header |

#### Conditional Field Logic

Fields now support conditional rules for both **required** status and **visibility**. Two new nullable properties are available on field objects:

- `required_conditions` — When set, overrides the static `required` flag. The field is required only when the conditions evaluate to true based on other field values.
- `visibility_conditions` — When set, the field is hidden unless the conditions evaluate to true. Hidden fields are not validated on submission.

Conditions use a nested group structure with logical operators:

| Schema | Description |
|--------|-------------|
| `ConditionSet` | Top-level container with `logic` (`and`/`or`) operator and an array of `groups` |
| `ConditionGroup` | Contains an array of `conditions`, combined using the opposite of the parent's logic operator |
| `Condition` | Evaluates a single field by `field_id`, `operator`, and optional `value` |

**Supported operators:** `is_filled`, `is_empty`, `equals`, `not_equals`, `contains`, `not_contains`, `greater_than`, `less_than`, `greater_than_or_equal`, `less_than_or_equal`

**Example — Make a field required only when another field is filled:**
```json
{
  "required_conditions": {
    "logic": "and",
    "groups": [

  }
```
